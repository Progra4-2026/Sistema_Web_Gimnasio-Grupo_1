1. Descripción general del sistema

Gimnasio PowerFit es un sistema web para la gestión de un gimnasio. Los visitantes consultan la información del gimnasio, envían consultas y se inscriben a una rutina o a un curso. Cada usuario inicia sesión según su rol:

  • Cliente: ve únicamente sus propias rutinas, consulta y actualiza su inscripción y puede desinscribirse.
  • Instructor: gestiona las máquinas y las rutinas de los clientes.
  • Administrador: gestiona los usuarios del sistema (clientes, instructores y administradores), los cursos y los parámetros del sistema.

Todas las vistas son parte de una única aplicación (SPA) y toda la información se obtiene de la base de datos MySQL mediante servicios RESTful; además se ofrece un servicio SOAP de ejemplo para consultar cursos.

2. Arquitectura

El sistema sigue una arquitectura cliente-servidor en tres capas. El navegador ejecuta la SPA de React, que se comunica con el backend únicamente mediante servicios RESTful en JSON. El backend aplica el patrón Modelo–Vista–Controlador y separa la lógica en capas; la persistencia se hace exclusivamente por medio del ORM.

Responsabilidades por capa

4. Diagrama de despliegue

En el entorno del proyecto los tres servidores corren en la misma computadora, cada uno en su propio puerto. El navegador descarga la SPA desde Vite y luego llama directamente a la API de Spring Boot; por eso el backend habilita CORS para el origen http://localhost:5173.

Nodo / entornoPuertoQué ejecuta
Navegador—La SPA de React; guarda la cookie de sesión JSESSIONID (http-only).
Node.js + Vite5173Sirve el frontend; agrega X-Frame-Options, X-Content-Type-Options y Referrer-Policy.
JVM + Spring Boot8080La API REST, la seguridad (sesión, roles, CORS, cabeceras) y el ORM.
MySQL3306La base de datos gimnasio_db.
En producción el mismo esquema se mantiene, pero publicando el sitio y la API con HTTPS. En ese caso Spring Security envía además la cabecera Strict-Transport-Security (HSTS), ya configurada.

5. Casos de uso

Actores: Visitante (sin sesión), Cliente, Instructor y Administrador. Los tres últimos especializan al actor Usuario autenticado, que puede iniciar y cerrar sesión.

Si un usuario sin sesión llama a un servicio protegido, la respuesta es 401; si tiene sesión pero no el rol requerido, 403. En el frontend, RutaPrivada redirige a /login sin sesión y muestra “Acceso denegado” cuando el rol no corresponde; después del login, cada rol llega a su sección.

6. Seguridad

6.1 Autenticación y autorización

  • Contraseñas: se guardan cifradas con BCrypt (hash + salt) mediante el PasswordEncoder de Spring Security; nunca en texto plano. Clientes en credenciales.password_hash; instructores y administradores en la columna password_hash de su tabla.
  • Inicio de sesión: un único endpoint (POST /api/auth/login) prueba el usuario como cliente (cédula), instructor (código) y administrador (código). El mensaje de error es el mismo si el usuario no existe o la contraseña es incorrecta.
  • Sesión: HttpSession con la cookie JSESSIONID, marcada como http-only (no accesible desde JavaScript), que expira tras 30 minutos de inactividad. Al iniciar sesión se renueva el identificador (changeSessionId, contra fijación de sesión) y se guarda el SecurityContext con el rol (ROLE_CLIENTE, ROLE_INSTRUCTOR o ROLE_ADMINISTRADOR).
  • Roles: @PreAuthorize en los controladores. Por ejemplo, hasRole('INSTRUCTOR') en máquinas y rutinas, hasRole('ADMINISTRADOR') en /api/admin/**, y #cedula == authentication.name para que un cliente solo modifique sus propios datos.

6.2 Protección contra inyección SQL

El sistema no construye sentencias SQL concatenando texto. Todo el acceso a datos pasa obligatoriamente por el ORM:

  • Los servicios usan únicamente los repositorios JpaRepository (findById, findAll, save, deleteById, existsById) y consultas derivadas como RutinaRepository.findByCliente_CedulaOrderByFechaDesc(Long cedula).
  • Hibernate traduce cada operación a una sentencia preparada (PreparedStatement) con parámetros ?. El valor que escribe el usuario viaja aparte, como dato, y nunca forma parte del texto SQL, así que un intento como ' OR '1'='1 se busca literalmente y no altera la consulta.
  • En el código no hay createNativeQuery, JdbcTemplate, Statement ni @Query: todas las consultas son métodos del repositorio.
  • Además, los datos se validan antes de llegar a la base (tipos numéricos para cédulas y códigos, longitudes y formatos).

Evidencia: con spring.jpa.show-sql=true la consola del backend muestra las sentencias con parámetros, por ejemplo:

select r1_0.id_rutina,r1_0.cliente,r1_0.fecha,r1_0.horas,r1_0.instructor,r1_0.maquina
from rutinas r1_0 where r1_0.cliente=? order by r1_0.fecha desc

Para ver además el valor enviado en cada parámetro se activa, en application.properties, logging.level.org.hibernate.orm.jdbc.bind=TRACE.

6.3 CORS

El frontend (http://localhost:5173) y la API (http://localhost:8080) son orígenes distintos, así que el navegador solo permite las llamadas si el backend lo autoriza. config/CorsConfig define una única configuración, que Spring Security aplica con http.cors(...):

ReglaValor
Orígenes permitidosLista blanca en app.cors.origenes-permitidos (application.properties): localhost:5173, 127.0.0.1:5173, localhost y 127.0.0.1. Nunca *.
MétodosGET, POST, PUT, DELETE y OPTIONS (preflight)
Encabezados permitidos / expuestosContent-Type, Accept / Location, X-Registros-Eliminados
CredencialesallowCredentials(true): deja pasar la cookie de sesión
Caché del preflight3600 segundos

Como CORS se aplica dentro del filtro de seguridad, también las respuestas 401 y 403 llevan los encabezados CORS, y el frontend puede mostrar el mensaje correcto en lugar de un error genérico de CORS.

6.4 Cabeceras HTTP de seguridad

CabeceraValorProtege contra
X-Frame-OptionsDENYClickjacking: nadie puede cargar la API o el sitio dentro de un iframe.
X-Content-Type-OptionsnosniffQue el navegador interprete un archivo con otro tipo (por ejemplo, ejecutar un JSON como script).

En el backend se configuran en SecurityConfig (http.headers(...)); en el frontend, en frontend/vite.config.js (server.headers y preview.headers). Para comprobarlas:

curl -I http://localhost:8080/api/health
curl -I http://localhost:5173/

6.5 Manejo de errores e integridad de datos

Ninguna respuesta incluye trazas del sistema (server.error.include-stacktrace=never). Los errores de negocio, validación y seguridad se devuelven como JSON {"mensaje": "...", "errores": {campo: mensaje}} con el código HTTP correspondiente (400, 401, 403, 404, 409 o 500); los 401/403 que genera el propio filtro de Spring Security usan el mismo formato. Reglas de integridad aplicadas en los servicios:

  • No se modifican llaves primarias ni foráneas (por ejemplo, al editar una rutina solo cambian la fecha y las horas): 400.
  • No se elimina un registro con relaciones (curso con inscritos, máquina usada en rutinas, instructor con rutinas): 409 con la explicación.
  • Cada actualización y eliminación confirma los registros afectados (registrosAfectados o el encabezado X-Registros-Eliminados).

7. Instrucciones de instalación

Requisitos

  • JDK 26 e IntelliJ IDEA (o Maven Wrapper incluido en backend/)
  • Node.js 20 o superior (incluye npm)
  • MySQL 8 o superior, en ejecución
  • Git

Pasos

1. Clonar el repositorio

git clone https://github.com/Progra4-2026/Sistema_Web_Gimnasio-Grupo_1.git
cd Sistema_Web_Gimnasio-Grupo_1

2. Crear la base de datos (crea gimnasio_db, las tablas y los datos de prueba)

mysql -u root -p < database/GIMNASIO.sql

Si la base ya existía de un entregable anterior, se vuelve a ejecutar el script: agrega las tablas administradores y parametros_sistema y la columna instructores.password_hash.

En PowerShell: Get-Content database\GIMNASIO.sql | mysql -u root -p

3. Configurar las credenciales de MySQL (solo si no son root/root): copiar backend/.env.example como backend/.env y completar DB_URL, DB_USER y DB_PASSWORD.

4. Levantar el backend: abrir backend/ en IntelliJ con el JDK 26 y ejecutar GimnasioBackendApplication, o desde la terminal:

cd backend
./mvnw spring-boot:run

Verificación: http://localhost:8080/api/health responde {"status":"ok"}.

5. Levantar el frontend (en otra terminal)

cd frontend
npm install
npm run dev

Abrir http://localhost:5173.
